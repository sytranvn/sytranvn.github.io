The Worst Performance Issue I Have Ever Faced

October 19, 2026 5-minute read
Performance
I have never seen any performance issue this bad in my entire life. No CPU spike, no OOM, our app just slowly die.

This is the first time in my life I have such relief after fixing a performance issue. It took me so long to troubleshoot and investigate. We went so fast with AI that we couldn’t even tell when it started. We started opening git blame and looking at each other code to find the issue but no one found it.

It started about a month ago. We were implementing an AI agent into an existing system. It uses java and Spring boot, not the most modern version, but still work fine, and migrating is not something bring value to the business compare to AI. So we keep it as it is. We had coded everything with Claude and some in-house models using proxy router. They weren’t the frontier models, but decent to use for work.

The more we used AI, the more specs we generated (following the SDD trend, you know). At one point, I don’t want to look at the specs and code anymore, reviewing code becoming giving approval to enable merge button. What’s the point of reviewing if you would just ask an other agent to review the code anyway.

And one day, we noticed that the APIs responded quite slowly. An API get user info takes 8 seconds to complete. Whenever a user login, they have to look at a disabled button spinning for 8 seconds. That is not acceptable. We can’t release any new features to production until this issue is fixed.

At first, we thought it was related to the Rabbit MQ dead letter messages. We often encounter similar issues with them in testing environment. The no-brainer solution is looking for the most problematic events DLQ and purge them. This seemed to fix it.

But, it still happened after a while. For testing environment, we only export logs, no tracing, no metrics.

Testing infra is also much lower than production. We tried to increase resource a little by little, but it didn’t help.

To me, this is the best and worst situation at the same time. As someone really interested in troubleshooting performance issues, I find it one of the fantastic beasts. But if we can’t figure it out, it will block everything we have been doing.

I decided we have to enable metrics and tracing to see what’s really going on. By the way, if you are thinking about setting up development environment and run profiling on it, we are on the same boat. I did, no problem found.

I suspect that we have created so many bad data records and they spawn many schedules. When all the schedules triggered, our small test containers can’t handle them. So I also plan for resetting test database, keep only one good record.

After deleting data, the charts looked calm. No schedules are triggered so no performance issue show up anymore 😬 .

But joy didn’t last long, it came back. The traces showed that we have many queries, Typical N+1 problem with ORM, I checked our DB reports, avg query is just 1-2ms. Even dozen of queries per request wouldn’t be that slow. However, between each query, there is a long delay, about 2 seconds. I tried the same function on local machine but it didn’t behave that way. So the only place this issue happen is on test environment.

Look into source code of function, only functions query data and map them to output DTO. But wait, nothing else except the logger to log query.

I realized I had previously seen some error log with logger at start up. It was GEFL related issue, but I didn’t pay attention. Basically, it send structured log to a centralized server like log stash. If it fails to establish connection to the server, it should have no impact on the application.

Even though it had high potential to be the root cause, I still don’t have concrete evident. There is no GELF config in the code, and I also don’t see any custom logging configuration in the helm charts to override it by devops. I asked Claude to write a POC script to prove that GEFL it is the root cause but it couldn’t.

I dug deeper into to source code and found a Github workflow file that downloaded some log4j2 configuration from a blob storage. This project was migrated to github recently and some old CI pipeline was converted to Github action. This step added a configuration XML file to the image, so to verify this, I need to pull it and check its content. And yeah, the GEFL configuration was there. It pointed to the exact host that was no longer online.

Every time the logger write a log, it failed to send data to the remote host and waited for 2 seconds, blocking the thread.Now I can ask Claude to use the same configuration and run the logger again to confirm the performance issue.

This step is now easy that I don’t have to look at the code anymore. I let Claude verify and only read summary.

I then contacted devops to remove the GEFL config as it was no longer needed.

I ran one final verification on test environment after deployment and everything worked smoothly again. No more painful blank loading screen, just sub second and responsive data fetching again.
